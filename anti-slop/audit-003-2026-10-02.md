## Findings

### 1. HIGH. Copy to Figma exports a different component from the one on screen
- Where: every component page with a preview (`src/components/FigmaFrame.tsx`, `src/lib/dom-to-svg.ts`).
- What: I compared each exported SVG with its live preview.
  - Button loading state (`/components/button`, click Delete, then Copy): the round spinner exports as three
    straight bars shaped like a "U". `box()` (`dom-to-svg.ts:173-184`) turns non-uniform borders into side
    rectangles and ignores `border-radius`. The spinner uses `border-2 border-current border-t-transparent rounded-full`.
  - QR Code Display: the dashed placeholder border exports as a solid line, because `box()` never reads `border-style: dashed`.
  - Accordion: the open item's chevron points up in the preview (`group-open:rotate-180`, `accordion.tsx:15`)
    but points down in the export. `icon()` (`dom-to-svg.ts:134-149`) copies the box but drops the CSS transform.
  - Layer names: the frame rect is hard-coded as `id="Frame"` (`dom-to-svg.ts:227`), and the first `<g>` also
    gets `id="Frame"`, so every export has duplicate ids. Every div or span gets "Frame", "Frame 2" through "Frame 7",
    numbered from the inside out because ids are assigned after the children are walked
    (`dom-to-svg.ts:218-219`). In Figma, the Tabs export shows "Frame / Frame 2 / Frame 3" instead of the three tab names.
  - Monospace text (the Table preview's `INV-0001`, code) exports as Urbanist (`FONT`, `dom-to-svg.ts:47`).
  - Shadows and Tailwind rings are dropped without notice (Dropdown `shadow-sm`, Modal `shadow-lg`, the hero
    chip's selected `ring-1`).
- Why: home says "Every preview can also be copied into Figma as editable layers". A designer pastes a
  square-bracket spinner, a solid border where the design has a dashed one, and 20 layers named Frame. That makes the claim untrue, and Figma is the source of truth this site points people to.
- Fix:
  - In `box()`, when `borderTopLeftRadius >= min(w,h)/2` and the side colors differ, emit one
    `<circle>` with the base color as its stroke, plus a second `<circle>` with `stroke-dasharray` covering the
    colored quarter.
  - When `styles[i] === "dashed"`, add `stroke-dasharray="4 3"`. Use `"1 2"` for dotted.
  - In `icon()`, read `getComputedStyle(svg).transform`. When it is not `none`, wrap the clone in
    `<g transform="matrix(...)" transform-origin="cx cy">`, or bake the rotation into
    `rotate(deg cx cy)`.
  - Give the frame rect `id("Background")`. Reserve the group id before walking the children (call `id()`
    first, then walk). Name a leaf element that holds text `Text / {text}` instead of `Frame`.
  - Pass `cs.fontFamily` through when it contains the code font, and set the stack to
    `IBM Plex Mono, monospace`.
  - Change the bar text (`FigmaFrame.tsx:62`) to "Paste into Figma as editable layers. Shadows are not
    included; apply the Natuna effect style."

### 2. HIGH. The Tabs preview draws the active indicator 24px above the divider
- Where: /components/tabs and the Tabs card on /components (`ComponentPreview.tsx:160-166`).
- What: the divider (`border-b`) is on the outer `py-6` wrapper, and the active tab's `border-b-2 pb-2` ends
  24px above it. I measured the underline at y=108 and the divider at y=134 in the export. The live
  preview shows the same gap. The underline floats in empty space and does not sit on the track.
- Why: this is the only picture of the component on its page, and it shows a broken tab bar. Copy to Figma passes the same mistake to designers.
- Fix: move the border to the tab row and remove the vertical padding from it.
  `<div className="py-6"><div className="flex justify-center gap-6 border-b border-gray-200 text-sm">` and give each
  tab `-mb-px pb-3`, so the active `border-b-2 border-blue-600` overlaps the 1px track.

### 3. HIGH. The QR Code page breaks its own rules and shows no code
- Where: /components/qr-code (`ComponentPreview.tsx:339-350`, rules in `components-data.ts:411-414`).
- What: Do says "Keep a quiet zone around the code and a white background", and Don't says "Place the code on a
  colored or dark background". In dark mode, the preview puts the code area on `#27303f`. The summary
  promises "its amount, recipient, and expiry", but the preview has no amount. "Valid for 15:00" can be read as
  a 15-minute countdown or as a 3 pm deadline. The code itself is a dashed empty box with "The QRIS code appears
  here", which looks like an upload slot.
- Why: a design system example that breaks its own Do and Don't rules on its own page teaches the opposite of the rule.
- Fix: wrap the code area in `theme-light bg-white` in both modes, with a solid `border border-gray-200`.
  Replace the dashed box with the `QrCode` glyph at `size={96}` on white, and change the caption to "Sample
  only, not a scannable code". Add `<div className="text-lg font-bold tabular-nums">Rp 25.000</div>` above the
  merchant, and change the expiry to "Expires at 15:00 WIB".

### 4. HIGH. On a phone, the props table hides the Default and Description columns
- Where: /components/button, /input, /avatar, /accordion, /badge at 390px (`[slug]/page.tsx:155-156`).
- What: `min-w-[40rem]` in a 342px box shows only Prop and Type. The Default column is cut off at the
  right edge, the Description column is fully off screen, and nothing shows that the table scrolls. Audit 002 #21 fixed
  the same problem on Themes, but not here.
- Why: Description is the column people read. On a phone, the table is the API reference with the explanations missing.
- Fix: below `sm`, render each prop as a definition block instead of a row:
  `<dl className="divide-y divide-gray-200 sm:hidden">` with name (mono, semibold), then `type` and
  `default` on one line in `text-xs text-gray-600`, then the description. Keep the table as
  `hidden sm:table`. If the table must stay, at least drop `min-w-[40rem]`, use `table-fixed`, and stack
  Type and Default into one column.

### 5. MEDIUM. Hero token callouts are wrong in one place and point at the bezel, not the part
- Where: Home hero at 1280px and wider (`HeroPhone.tsx:18-23`, `64-80`, title at `94`).
- What: the callout says "Subheader 18 / 26 Semibold", but the title renders at 18/28 (`text-lg`, computed
  `line-height: 28px`). Each leader is a 16px line that stops at the device bezel, about 24px outside the
  element it names. "Rounded/8 Height/48" sits 18px below the button's center, and "shadow-xl" points at the
  Note label. Between the Note field and the Send button there is a 64px empty band (`min-h-[32rem]` plus `mt-auto`).
  Below 1280px the callouts disappear completely, so at 1024px the hero is a plain phone.
- Why: the comment says "the picture is also documentation". A wrong value in the hero is the first
  thing a designer checks, and the loose leaders make the annotations look decorative.
- Fix: give the title `leading-[26px]`, so it matches the Subheader token. Extend each leader to the element
  (`w-10` and position `top` from the measured centers: 23%, 30%, 52%, 69%), and point shadow-xl at the device corner. Remove
  `min-h-[32rem]` and use `gap-4` with the button directly after the note. From `lg` to `xl`, show the four
  tokens as a two-column `dl` under the phone instead of hiding them.

### 6. MEDIUM. At tablet widths, the header wraps the wordmark onto two lines
- Where: every page from 768px to about 850px (`Header.tsx:25-31`, `CommandSearch.tsx:94`).
- What: at 768px, "Natuna / Digilab" stacks to two lines (the span measures 48px tall), because the
  four nav links, the 208px search field and two icon buttons all appear from `md` up.
- Why: the brand mark breaking is the first thing a tablet visitor sees, and it makes the header look unplanned.
- Fix: add `whitespace-nowrap` to the wordmark span. Change the search button to `sm:w-11 lg:w-52`, and show
  its "Search" label and kbd only from `lg` (`hidden lg:block`), so at `md` it is an icon button.

### 7. MEDIUM. Loading turns every Button variant into the disabled gray
- Where: `src/ui/button.tsx:6,39-41`, seen on /components/button (click Delete) and in the Button thumbnail ("Saving").
- What: `loading` sets `disabled`, so `disabled:bg-gray-100 disabled:text-gray-500` replaces the variant.
  The red "Delete" becomes a gray "Deleting", and a primary "Saving" looks like a disabled button.
- Why: a loading action is in progress, not unavailable. Losing the color hides which action is running, and
  it contradicts the prop doc ("The label stays so the width does not change"), which implies the button
  otherwise stays the same.
- Fix: keep `disabled` for blocking clicks, but scope the gray to real disabled buttons:
  `aria-disabled:` styles for disabled only, or build the class as
  `${disabled ? disabledCls : ""}` and give loading `cursor-progress opacity-90` with the variant colors kept.

### 8. MEDIUM. A component has a different name on the overview and on its own page
- Where: /components cards (tracker names, `natuna-tracker.ts:44-94`) compared with the sidebar, h1 and Related
  (`components-data.ts` names).
- What: overview name, then page name: "Cards" vs "Card", "Dividers" vs "Divider", "Dropdown" vs "Dropdown
  Menu", "Input Field" vs "Input", "Tooltips" vs "Tooltip", "Modal / Dialog" vs "Modal", "Spinner / Loader" vs
  "Spinner", "Menu (Dropdown Action)" vs "More Menu". Clicking "Menu
  (Dropdown Action)" opens a page titled "More Menu". The Atoms description says "buttons, badges, inputs"
  (`natuna-tracker.ts:36`), but Input Field is a Molecule. The nav says "Docs", while that page's h1, the home row, and the
  Ctrl K result say "Introduction".
- Why: readers check that they landed in the right place by the name. When names change between pages, the catalog feels like two lists stitched together.
- Fix: use one name per component. Render `getComponent(item.slug)?.name ?? item.name` on overview cards, and
  keep the Notion name only in a `title` attribute. Change the Atoms description to "The smallest building
  blocks: buttons, badges, avatars, and other single-purpose elements." Rename the nav item to "Introduction",
  or rename the page to "Docs". Pick one and use it in the nav, the footer, the h1 and the home row.

### 9. MEDIUM. The status vocabulary no longer adds up after "Not tracked" was added
- Where: /docs > Component status (`docs/page.tsx:83`), `components-data.ts:664,674-686`.
- What: Docs says "Every component carries one of four statuses", but the sidebar, Related and Ctrl K now
  show a fifth, "Not tracked", and Docs does not explain it. "On Review" maps to `beta`, which is labeled
  "In progress" in the sidebar and Related, while the overview and status row say "In review". So the same component
  would carry two labels as soon as one enters review. "Not tracked" and "Planned" share
  `bg-gray-100 text-gray-700`, so the Button page's Related list cannot tell them apart.
- Why: status is the trust signal this site has worked hardest on. Two label sets and an undocumented
  fifth status undo that work.
- Fix: add `review` to `ComponentStatus` and map "On Review" to it, labeled "In review" with the
  `statusStyle` tone. Give `untracked` a dashed outline instead of a fill: `border border-dashed border-gray-400
  bg-transparent text-gray-700`. In Docs, write "one of four tracker statuses", add a fifth row "Not tracked:
  Not in the component tracker. No design sign-off and no code; treat it as a sketch.", and use the
  Not tracked badge style.

### 10. MEDIUM. Code blocks repeat themselves and switch language separately
- Where: component pages with code (`[slug]/page.tsx:119,134`, `CodeBlock.tsx:53`, `component-docs.ts:22,121`).
- What: Import and Usage each have their own TS/JS switch (`useState` per block), so a JavaScript reader has to switch
  twice on every page. The Usage block starts with the same import lines as the Import block 200px above it. The
  TS import lines bring in `type ButtonProps` and `type InputProps`, which the usage code never uses, so a
  pasted snippet fails `no-unused-vars` and `noUnusedLocals`.
- Why: the page promises "The code below it is the same code". Code that fails lint on paste and a switch that
  does not stay set make the code blocks look careless.
- Fix: keep the language in one store (a small context in `CodeBlock`, saved to `localStorage("code-lang")` inside
  try/catch), so every block on the site follows it. Drop the unused type imports from the button and input
  `importCode.ts`, or use them in the usage code (`const variant: ButtonProps["variant"] = "secondary"`).
  Keep the Import block, and start Usage after the imports with `collapseAfter` adjusted, or
  remove the Import section and label the usage block "Usage, with imports".

### 11. MEDIUM. Related lists every component in the category
- Where: all detail pages (`[slug]/page.tsx:41,207-223`). For example, /components/card lists 15 items.
- What: Related is `components.filter(category === current)` in data order. On Card, it runs from Avatar to
  QR Code Display and is longer than the rest of the page. On Button, it puts "Not tracked" items above Ready
  ones.
- Why: a list of 15 is a second index, not a recommendation, and it pushes the footer two screens away on a phone.
- Fix: add `related?: string[]` to `ComponentMeta` and curate three or four per component (Card: Badge, Button,
  Empty State, Skeleton). Fall back to the same category sorted Ready first and sliced to 4, with a "See all
  {category} components" link to `/components`.

### 12. MEDIUM. Home rhythm: one oversized gap, one duplicated section, one empty statistic

### 13. MEDIUM. Token copy disagrees with the Foundation page

### 16. MEDIUM. The type-scale fix from audit 002 #7 covered Home only
- Where: section headings on all other pages.
- What: h2 is `text-3xl sm:text-4xl` on Home, `text-3xl` on Foundation (`foundation/page.tsx:156` and so on),
  `text-2xl` on Docs, Themes, Components and the detail pages. Some have `tracking-tight` and some do not
  (`[slug]/page.tsx:113` has it, `:154` does not). Section spacing on detail pages alternates `mt-12` and `mt-14`.
- Why: on a site that documents a type scale, headings for the same level vary by page, so the pages do not read as one system.
- Fix: add `.h2 { @apply text-2xl sm:text-3xl font-bold tracking-tight text-gray-900 }` in `globals.css` and use it
  for every section h2, Home included. Use `mt-14` for every detail-page section.

### 17. LOW. Preview wells are invisible in light mode and boxed in dark mode
- Where: Home "Ready in Figma" tiles (`page.tsx:201`), /components thumbnails (`ComponentOverview.tsx:30`).
- What: the wells use `bg-canvas` inside `bg-surface`. In light mode both are `#ffffff`, so previews float
  with no frame. In dark mode, `#19212e` inside `#27303f` makes a clear inset box.
- Why: the two modes give the same tile different structure, which breaks mode parity.
- Fix: use a token that differs in both modes. Use `bg-gray-50` (light `#f1f5f9`, dark `#27303f`), and change the
  tile to `bg-canvas` in dark, or add `--color-well` (`#f1f5f9` light, `#19212e` dark) and use `bg-well`.

### 20. LOW. Guidance copy reads like a template
- Where: `components-data.ts`, for example Tabs (`:223-224`), Card (`:134-136`), and Button Group (`:57-58`).
- What: "Limit to a manageable number of tabs (up to ~6-7)", "Use more than 4-5 items", "Use to group content
  into digestible, scannable sections". These are hedged ranges with a tilde, and generic phrasing that could
  describe any system. Card's Do asks for "title, body, action", but the Card preview has no action. The Tabs
  Don't, "Use tabs for sequential steps: use a stepper instead", reads as an instruction to use tabs.
- Why: vague rules give teams nothing to check against, and the preview breaks the Card rule beside it.
- Fix: state one number and the reason. Tabs: "Keep it to five tabs or fewer. More than that wraps on a 360px
  screen." Button Group: "Use two to four options." Card usage: "Use a card for one record, such as a bill or
  a transfer, that the user can act on." Rewrite the Tabs Don't as "Don't use tabs for steps that must happen in order.
  Use a Stepper." Add `<Button size="md" className="mt-3 w-full">Pay now</Button>`-style markup (a styled span in
  the preview) to the Card preview.
