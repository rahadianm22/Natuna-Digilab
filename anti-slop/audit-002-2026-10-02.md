# antislop audit 002, 2026-10-02

Scope: every route (/, /docs, /foundation, /components, /components/button, /input, /accordion, /tabs,
/themes, /privacy, 404) at 1440px and 390px, light and dark, captured in Edge with Playwright after
scrolling each page. I also read the source in src/app, src/components, src/ui and src/lib.
Nothing from audit 001 is reported again. The Copy to Figma / Download SVG bar (`FigmaFrame.tsx`) was
added while I was reviewing. It appears below only where it shares a problem with other controls (tap targets).

Measured at 390px: no page overflows horizontally. Every interactive element under 44px is listed in
finding 4.

## Findings

### 1. HIGH. Five components that are neither tracked nor built are shown as Ready
- Where: sidebar on every component page, the "Related" list, and Ctrl+K search.
- What: `button-group`, `icon-button`, `link`, `code-block` and `select` are `status: "stable"` in
  `src/lib/components-data.ts` (for example lines 51-93). They are not in `natuna-tracker.ts`, so the
  tracker override at the end of the file never runs for them. The sidebar hides the status label for
  `stable` (`ComponentSidebar.tsx:80`), so they look ready. "Related" shows a green **Ready** badge
  (`StatusBadge`, seen under Button > Related in dark mode), and Ctrl+K shows "Ready"
  (`CommandSearch.tsx:29`). Only the detail page says "Not in the tracker yet".
- Why: the site tells readers that components with no design sign-off and no code are safe to use. Audit 001 #1 fixed this same honesty problem for tracked components.
- Fix: add a fourth `ComponentStatus` value, `"untracked"`, with `statusText.untracked = "Not tracked"` and
  `statusTone.untracked = "bg-gray-100 text-gray-700"`. Set it on these five entries. In
  `ComponentSidebar.tsx:80`, show the label for everything except `stable`, so "Not tracked" appears.

### 2. HIGH. The Themes "Color roles" table does not match the tokens the site uses
- Where: /themes, the table (`src/app/themes/page.tsx:11-17`).
- What: the table says dark Soft gray is `#4b5565`, but `globals.css:162` sets `gray-50` to `#364152`.
  It says dark Text secondary is `#f1f5f9`, but `gray-600` in dark is `#9aa4b2` (`globals.css:168`).
  It says Main blue is `#0276e3`, but every filled button uses `--color-brand: #026acc`
  (`globals.css:25`). The copy beside the table says Main blue "always carries white text". On
  Foundation, the site itself shows white on `#0276e3` as 4.47:1, which fails AA.
- Why: a token page whose values are wrong is worse than no token page. Engineers will copy these hex values.
- Fix: generate `roles` from the same values `globals.css` uses. Add a role for each one a component
  asks for: Background `#ffffff/#19212e`, Surface `#ffffff/#27303f`, Border `#d0d5dd/#364152`, Text primary
  `#19212e/#f1f5f9`, Text secondary `#4b5565/#9aa4b2`, Brand fill `#026acc/#026acc`, Link
  `#026acc/#67b6ff`, Danger `#bb3a3b/#bb3a3b`. Change the copy to: "Brand fill stays #026acc in both
  modes because it carries white text at 5.34:1."

### 3. HIGH. Code and hex values are set in a proportional sans, so 1 and l look the same
- Where: every code block, the props table, Foundation swatches, and the token chips.
- What: `globals.css:15` maps `--font-mono` to Urbanist, and `.font-mono-code` (`globals.css:265`) does
  the same. On Foundation at 390px, `#d1e9ff` reads as "#dle9ff" and `#001b33` reads as "#00lb33". In
  the Button usage block, two-space indents collapse to about 6px, so nesting is hard to follow (home,
  "See it, try it, copy it").
- Why: people copy hex values and code from a design system site, and here they can misread them.
- Fix: load a monospace font in `layout.tsx` (`JetBrains_Mono` from `next/font/google`, variable
  `--font-code`). Set `--font-mono: var(--font-code), ui-monospace, SFMono-Regular, Menlo, monospace` and
  use the same stack in `.font-mono-code`. Keep Urbanist for prose and for numbers in tables.

### 4. HIGH. Many tap targets are under 44px on a phone
- Where: measured at 390px on every page.
- What: header search, theme, GitHub and menu buttons are 36x36 (`Header.tsx:57,67`,
  `ThemeToggle.tsx:34`, `CommandSearch.tsx:93` use `h-9`). The code block TS/JS tabs, Copy and Expand are
  32px tall (`CodeBlock.tsx:94,112,120` use `min-h-8`). The status filter chips are 36px
  (`ComponentOverview.tsx:113`). The hero quick amounts and Light/Dark radios are 36px
  (`HeroPhone.tsx:139,174`). Copy to Figma and Download SVG are 36px (`FigmaFrame.tsx:53`). The default
  `Button` size is 40px (`button.tsx:17`, `min-h-10`). The breadcrumb link is 17px tall.
- Why: this breaks the house rule, and the sticky header buttons are the controls people tap most.
- Fix: use `h-11 w-11 sm:h-9 sm:w-9` on header icon buttons, and `min-h-11 sm:min-h-8` on CodeBlock
  controls. Use `min-h-11 sm:min-h-9` on chips, hero controls and FigmaFrame actions, and
  `md: "min-h-11 sm:min-h-10 px-4 text-sm"` on Button. Give the breadcrumb link `inline-flex min-h-11 items-center`.

### 5. HIGH. Each page starts content at a different left edge
- Where: all pages at 1440px. Measured x positions of the logo and h1.
- What: the header logo is at 24px, because the header row has no max-width (`Header.tsx:23`). The h1 is
  at 168px on Home, Docs and Foundation (`max-w-6xl`), 104px on Components (`max-w-7xl`), 232px on Themes
  (`max-w-5xl`) and 336px on component pages. The footer is at 104px (`Footer.tsx:26`, `max-w-7xl`). On
  Home, the footer logo and the content above it are 64px out of line on both sides.
- Why: when the left edge moves from page to page, the layout looks unplanned and harder to scan.
- Fix: define one container, `mx-auto w-full max-w-7xl px-6`, and use it in the header inner row,
  the footer, and every page wrapper. Narrow the reading column inside it (`max-w-3xl` for prose), not the
  container. Component pages keep the sidebar and align it to the same 24px gutter.

### 6. HIGH. The component catalog uses two different groupings
- Where: /components compared with every /components/[slug] page.
- What: the overview groups by Atoms and Molecules (`natuna-tracker.ts` `trackerGroups`). The sidebar,
  breadcrumb and Related list group by Action, Display, Form, Navigation, Overlay, Feedback and
  Documentation (`components-data.ts:19-27`). The breadcrumb "Components / Action" is plain text that
  points to a group the overview never shows. One component can be a "Molecule" on the overview and an
  "Action" in the sidebar.
- Why: readers lose their place moving from the overview to a detail page, and "Related" means something
  different from what the overview implies.
- Fix: choose one grouping. The Figma-facing Atoms and Molecules split is what the tracker owns, so use it in
  `ComponentSidebar` and the breadcrumb, and show the purpose category (Action, Form and so on) only as
  the "Category" row. Alternatively, add the categories as a second filter on the overview, and make the breadcrumb category a
  link to `/components?category=action`.

### 7. MEDIUM. Headings do not follow the site's own type scale
- Where: section headings site-wide.
- What: Foundation documents Header 1 as 32/44 and Header 2 as 28/40. The site uses h2 at `text-5xl`
  (`page.tsx:107,144`), `text-4xl` (`page.tsx:168,204,225`), `text-3xl` (Foundation), and `text-2xl`
  (Docs, component pages, Themes). Two home h2s end with a period ("One foundation under every
  screen.", "See it, try it, copy it.") and three do not.
- Why: a design system site that ignores its own scale weakens its own guidance, and the uneven sizes
  blur the hierarchy.
- Fix: add `.h1` (`text-4xl sm:text-5xl font-extrabold tracking-tight`) and `.h2` (`text-2xl sm:text-3xl
  font-bold tracking-tight`) in `globals.css` and use them everywhere. Keep `.display` only for the home h1.
  Remove the trailing periods from the h2s.

### 8. MEDIUM. The home "numbers" band is filler and repeats itself
- Where: Home, the band below the hero (`page.tsx:34-39`, `93-102`).
- What: "2 modes, light and dark" and "7 text styles" (a hard-coded `7`) are not progress or scale.
  They pad the band out to four cells. The figure 51 then appears again in "Where the build stands" and in
  "Where to go next". At 390px the band takes about 640px of height (`py-10`, 2x2 grid, `text-5xl`).
- Why: house rule, no fake or padded stats. It also pushes the real content down on phones.
- Fix: delete the band. Move "88 color tokens in 8 ramps" into the Foundation section's paragraph
  ("88 color tokens in 8 ramps, seven text styles, five radii..."). The build-status section already
  carries the 51.

### 9. MEDIUM. "Ready to use" mixes Figma documentation frames with UI components
- Where: Home, "Ready to use" grid (`page.tsx:28-31`, `203-221`).
- What: four of the nine tiles are Guideline, Headline, Artboard and Document. These are Figma page
  templates, not components a product team uses. The section sits right after "See it, try it, copy
  it", which implies code, but only Button, Input, Avatar and Accordion exist in `src/ui`.
- Why: it inflates readiness and blurs the line between the Figma kit and the React kit.
- Fix: filter out `category === "Documentation"`. Retitle the section "Ready in Figma", and add a small
  `Badge tone="info"` reading "In code" on tiles whose slug has an entry in `componentDocs`.

### 10. MEDIUM. Thumbnails are clipped or inconsistently aligned
- Where: Home "Ready to use" and the /components cards.
- What: the Input tile on Home clips its first label against the top of the `h-36 overflow-hidden` box
  (`page.tsx:210`). On /components the Button thumbnail cuts off its "Primary" row and "Large" button
  (`ComponentOverview.tsx:22-25`, `h-32` with `scale-[0.7]`). The Headline preview is left-aligned while
  the others are centered. The Avatar preview's fourth avatar, "D" (name "Digilab"), looks like a bug.
- Why: cropped thumbnails look broken and contradict the claim that these are real components.
- Fix: add a `variant="thumb"` path in `ComponentPreview` that renders one compact example per component
  (Button: one primary and one ghost; Input: one field with hint). Make the headline preview `text-center`.
  Remove the fourth avatar.

### 11. MEDIUM. Previews use template placeholder copy and one false claim
- Where: /components cards and planned component pages (`ComponentPreview.tsx`).
- What: "Card title", "Supporting description text goes here." (line 111), "Reviewer name", "Comment
  text goes here and wraps onto a second line when it is long." (line 280), "Merchant name", "Sender
  name", "Bank name", "[QR CODE]" (line 345), "Balance shown here", "natuna.ui / components / Button",
  "Volume". The Code Block preview shows `npm install @natuna/ui` (line 117), which Docs says does not exist.
- Why: lorem-style labels make the system look unfinished. The npm line brings back the claim audit 001 #2 removed.
- Fix: use the hero's Indonesian payment context throughout. Examples: Card "Electricity bill / Due 12
  Oct". Comment "Rina Putri, 2 hours ago: Please check the transfer limit before release." Transaction
  "Indomaret Cikini / -Rp 125.000" and "Budi Santoso / +Rp 500.000". Label text "Bank / BCA". Breadcrumbs
  "Home / Transfers / Details". Slider "Daily limit, Rp 0 to 10 jt". QR: render a real SVG grid, or the
  text "QRIS code appears here" without brackets. Code block: `import { Button } from "@/ui";`.

### 12. MEDIUM. Dark mode gives three gray steps the same value, which removes hover and state feedback
- Where: everything that uses `gray-50/100/200` in dark mode.
- What: `globals.css:162-164` sets `gray-50`, `gray-100` and `gray-200` all to `#364152`. As a result,
  Secondary Button `bg-gray-100 hover:bg-gray-200` (`button.tsx:11`) has no hover change in dark mode, and
  neither do the hero quick-amount chips (`HeroPhone.tsx:140`). Disabled and Secondary buttons share one
  fill. `border-gray-200` on `bg-surface` measures 1.29:1, so card and table borders nearly disappear.
- Why: dark mode loses the feedback that light mode has, so the two modes are not equal.
- Fix: spread the steps across the Slate ramp. In dark mode: `gray-50: #27303f`, `gray-100: #364152`,
  `gray-200: #4b5565`, `gray-300: #697586`. Then re-check `bg-gray-50` wells against `bg-surface`. They
  become equal, so wells should use `bg-canvas`.

### 13. MEDIUM. Shadow specimens cannot be read in dark mode
- Where: /foundation > Effect > Shadow, dark mode (`foundation/page.tsx:345-347`).
- What: the tile (`bg-surface #27303f`) sits on a lighter well (`bg-gray-50 #364152`). The tiles look
  like recessed holes, and none of the four shadow levels is visible.
- Why: this specimen exists to show elevation, and in dark mode it shows the opposite.
- Fix: wrap the shadow `<ul>` in `className="theme-light rounded-2xl p-6"` and add the caption "Shadows
  are specified on light surfaces. In dark mode, elevation comes from a lighter surface." If dark-mode
  elevation should be shown too, add a second row with tiles `bg-gray-100` on `bg-canvas`.

### 14. MEDIUM. Input borders and focus rings are below 3:1
- Where: `src/ui/input.tsx:24`, the sidebar filter (`ComponentSidebar.tsx:27`), the overview search, and preview inputs.
- What: `border-gray-300` (#cdd5df) on white is about 1.4:1, and #4b5565 on #27303f in dark is similar.
  The focus ring `ring-blue-200` (#9aceff) is 1.66:1 on white, and in dark (#015099 on #27303f) it is 1.65:1.
  The sidebar filter shows focus only as a 1px border color change.
- Why: WCAG 1.4.11 requires the boundary of a field and its focus indicator to reach 3:1. The Input
  component is marked Ready, so this ships to every product that uses it.
- Fix: rest state `border-gray-500` (#697586, 4.8:1 on white; #9aa4b2 in dark). Focus state
  `focus-visible:ring-2 focus-visible:ring-blue-600 focus-visible:ring-offset-1
  focus-visible:ring-offset-canvas`. Remove `focus:outline-none` from the sidebar filter, or give it the same ring.

### 15. MEDIUM. The hero "Screen mode" radio group does not follow radio keyboard behavior
- Where: Home hero (`HeroPhone.tsx:166-181`).
- What: it uses `role="radiogroup"` and `role="radio"`, but both buttons are in the tab order and arrow
  keys do nothing.
- Why: screen reader users are told it is a radio group, then the keys they expect do not work.
- Fix: the simple route is two buttons with `aria-pressed` inside `role="group"`. Otherwise, add
  `tabIndex={mode === m ? 0 : -1}` and an `onKeyDown` that maps ArrowLeft and ArrowRight to `setMode` and
  moves focus, as `CodeBlock.tsx:71-77` already does.

### 16. MEDIUM. Component pages on a phone show two identical hamburger icons and a crowded header
- Where: /components/* at 390px.
- What: the header menu button uses `List`, and directly below it the "All components" bar also starts
  with `List` (`ComponentSidebar.tsx:126`). The header row holds four bordered 36px icon buttons next to
  the wordmark.
- Why: two identical icons for different menus make readers guess which one opens what, and the crowded header looks unfinished.
- Fix: in `ComponentMobileNav`, remove the leading `List` icon and keep the label plus the trailing caret
  (or use `SquaresFour`). Below `md`, move the GitHub link into the mobile nav panel (`Header.tsx:52-60`
  with `hidden md:flex`), so the header keeps three controls.

### 17. MEDIUM. Planned pages say "not built" twice in a row
- Where: /components/tabs and every planned page (`[slug]/page.tsx`, the `role="note"` block and the
  `codeNote` paragraph under Example).
- What: "Not built yet. The example shows the intended design, not a released component." is followed
  about 80px later by "The React component is not built yet. The example shows the design only." The
  note box is also `max-w-2xl`, so it stops 128px short of the content column, unlike the rules above it.
- Why: repeating the message adds noise, and the box that stops short makes the column look ragged.
- Fix: delete the `role="note"` block. Keep `codeNote` under the Example heading. Keep the "Planned" status line in the status row.

### 18. MEDIUM. "Build day 8" means nothing to readers
- Where: /components cards, the component status row, and the Docs status definitions.
- What: build days appear everywhere, but no page says what day 1 is, how many days there are, or when a day falls.
- Why: a schedule with no reference point does not tell anyone when a component will arrive.
- Fix: add one sentence to Docs > Component status: "The build plan runs 21 build days. Build day 1 started
  on <date>; components move to Ready when their day's work passes review." Render "Build day 8 of 21" on
  cards and in the status row. If dates exist, show "Build day 8, planned week of 13 Oct".

### 19. MEDIUM. The overview lists components in Notion row order
- Where: /components (`ComponentOverview.tsx:137`, which uses `visible` in tracker array order).
- What: Atoms run Badge, Toggle, Separator, Headline, Artboard, Comment, Label Text, Avatar... This is
  neither alphabetical nor ordered by status or build day.
- Why: a catalog of 51 items needs an order people can predict, or they scan the whole grid every time.
- Fix: sort `items` by `statusOrder` index and then `name.localeCompare`, so Ready comes first.
  Alternatively, sort alphabetically and add a "Sort: A to Z / Build day" toggle.

### 20. MEDIUM. Button guidance contradicts itself
- Where: /components/button, "When to use" compared with "Don't" (`components-data.ts:37-38` and `47`).
- What: "When to use" lists "navigation", and the third Don't reads "Use a button for navigation. If it
  only takes the user to another page, use a link instead."
- Why: a design system page cannot give opposite rules for the same case.
- Fix: change usage to "Use it for actions: submitting a form, confirming a choice, opening a dialog, or
  starting a process. For moving to another page, use a Link, styled as a button only when it is the main
  call to action."

### 21. MEDIUM. The Themes table scrolls sideways on a phone with no cue
- Where: /themes at 390px (`themes/page.tsx:71`, `min-w-[28rem]`).
- What: the Dark column is cut off at the right edge, and nothing shows that the table scrolls.
- Why: readers on phones never see the dark values, which are half of what the table documents.
- Fix: remove `min-w-[28rem]`. In each cell, stack the swatch above the hex (`flex-col sm:flex-row
  items-start gap-1.5`), so three columns fit in 342px.

### 22. LOW. The background blur specimen sits on a decorative gradient
- Where: /foundation > Effect > Background blur (`foundation/page.tsx:363`).
- What: `bg-gradient-to-br from-blue-600 via-emerald-500 to-amber-400` with rotated bars. It reads as
  a decorative gradient, especially in dark mode.
- Why: house rule, no decorative gradients. It also does not show the real use case.
- Fix: put a real UI snippet behind the blur, such as the transaction list preview or the bill card from
  Themes, so the specimen shows "content behind an overlay".

### 23. LOW. Phone layout has very large vertical gaps and uneven stacked buttons
- Where: Home and 404 at 390px.
- What: every home section uses `py-24` (`page.tsx:105,142,166`) plus bordered bands, which leaves about
  190px of empty space between sections on a phone. The hero CTAs stack at different widths (both
  `buttonStyles` with no width, `page.tsx:65-72`), as do the 404 buttons (`not-found.tsx:25-37`). In the
  type card (`page.tsx:124`), the radius chips wrap to two rows beside the "Aa", which leaves an awkward empty corner.
- Why: the page feels padded on a phone, and the ragged buttons look unfinished.
- Fix: use `py-16 sm:py-24` on home sections. Add `w-full sm:w-auto` to stacked CTA links. In the type card,
  use `grid-cols-1 sm:grid-cols-[auto_1fr]`, so "Aa" sits above the details on a phone.

### 24. LOW. The dark-mode hero panel is too bright, and the phone outline disappears
- Where: Home hero in dark mode (`HeroPhone.tsx:60,82`).
- What: the `bg-[#026acc]` panel keeps full saturation on a `#19212e` page and is the brightest thing on
  screen. Where the phone extends above the panel, its `#0d121c` bezel blends into the canvas.
- Why: the hero outshines the headline and loses its outline.
- Fix: add `dark:bg-[#015099]` (blue-800) to the panel through a `.dark &` selector or a token
  `--color-hero-panel`. Change `ring-white/10` to `ring-white/20` on the device frame.

### 25. LOW. Small copy loose ends
- Where: Import block, Privacy, Home "Where to go next".
- What: the Button import snippet includes `import { useState } from "react"` (`component-docs.ts:19-22`),
  which belongs to the demo, not the component. Privacy says "Open an issue on the project repository" with no
  link (`privacy/page.tsx:39`). The "Where to go next" rows (`page.tsx:229-232`) are links that look like
  plain text until hover, with no color or underline.
- Why: small gaps like these add up and make the site look unfinished.
- Fix: make the import read only `import { Button, type ButtonProps } from "@/ui";` and move `useState` into the
  usage block. Link "Open an issue" to `ISSUES_URL`. Give the route titles `text-blue-700` and
  `group-hover:underline underline-offset-4`.
